# Steward inventory integration

This fork preserves AutoRetainer's assembly, InternalName, display name, commands, configuration and existing IPC. The icon is a recolouring of the original emblem in the maintained forks' green-to-magenta palette. Existing functionality remains enabled and configured in AutoRetainer.

The `AutoRetainer.InventoryPolicy.*` protocol is version 6; update Steward and this bridge together. `Connect(contentId, callback)` claims a current character and persists only that ownership marker in AutoRetainer's own configuration. The sole supported callback is `Steward.InventoryPolicy.Evaluate`. `Heartbeat` renews a five-second lease. `Detach` explicitly restores the original rules. Missing callbacks, invalid responses, stale leases and policy exceptions hold managed item actions. Characters never connected behave as upstream. `OwnsHandoff(contentId)` proves that the current postprocess lock belongs to the connected Steward character. Menus and retrieval require that ownership. A lease watchdog releases a stranded recorded Steward handoff without unlocking another plugin's handoff.

`AcquireControl`, `OwnsControl` and `ReleaseControl` provide separate owned standalone coordination. Acquisition requires the connected character, idle AutoRetainer and an unset general suppression flag. While acquired, AutoRetainer reports busy, pauses its main update loop and denies its item actions. Expiry, character change or shutdown releases the recorded control. Release is idempotent and cannot release a different character's control. The general `IPC.Suppressed` value is never changed by this protocol.

Control/review holds maintain AutoRetainer's existing YesAlready and TextAdvance pause requests. GC native commit gates allow one Deliver and one HQ Yes per transaction; waiting for acknowledgement never retries a commit. Uncertain GC state persists `CompanionPolicyFaults`, holds managed actions/main-loop work and notifies `Steward.InventoryPolicy.Fault`. Steward can also request a bilateral `Hold`. `HasFault` lets the companion recover that hold after reload; `ClearFault` requires a connected owner, released control/handoff and closed confirmation dialogs. A deliberately detached character retains original upstream behaviour, while the review marker is retained for any later reconnection.

Before candidate processing and submission, AutoRetainer asks Steward with JSON containing Version, Character, Action, ItemId, Quantity, Container and Slot. Only the literal response `Allow` authorizes handling. Existing explicit AutoRetainer protection lists and enabled features still apply. Vendor, desynthesis, GC delivery, discard and armoire paths have policy gates; managed discard is denied by Steward. `Run` delegates to existing AutoRetainer work. `Menu` and `Retrieve` are restricted to an owned retainer postprocess handoff; retrieval uses AutoRetainer's existing native action and validates the source slot and free space.

Managed discard is stopped before scheduling and at the final confirmation. GC reward/HQ confirmation requires a pending item with unchanged inventory, matching reward text, fresh permission and an unexpired ownership record. The HQ confirmation must also identify the previously validated reward window as its parent/host. Unknown native layouts hold. Quick-sell and low-level sale helpers also gate automated actions. Desynthesis rechecks before its final native confirmation.

Glamour Log exposes bulk dresser storage without per-item submission callbacks. The bridge therefore holds managed bulk transfers; a one-time candidate check cannot protect actions after delegation or unload. The upstream bulk workflow remains unchanged for unmanaged characters. The dresser-opening workflow has an additive leave-open overload for Steward. Individually checked native transfers remain available, with unknown outfit dialogs held.

Upstream vendor/desynthesis lists remain selectors. Steward filters their candidates; it does not overwrite those lists or force every unwanted item into unconditional vendor sale. GC delivery already enumerates native delivery candidates. In particular, a skipped GC action or capped seals must not be interpreted as ineligibility.

Third-review hardening: guard-relaxing save failures roll back in-memory state. Successful explicit recovery resets the old GC pending state and one-shot gates after persistence, preventing immediate re-latching. An active unfaulted journal cannot be cleared. Final slot checks repeat identity/quantity/flags and explicit AutoRetainer protection after the callback. Managed desynthesis also binds the agent's selected item snapshot before confirmation. Unverified/mismatched native data holds. Fault notification is still attempted if maintaining dialog pauses throws.

Repeated-review hardening replaces the assumption that `EzConfig.Save` throws: the pinned writer catches disk errors. Companion ownership, faults and pending markers now live in a separate synchronous `steward-policy.json` ledger under this plugin's config directory. It migrates old companion markers once and is authoritative thereafter; ordinary configuration imports cannot detach it. Unknown/corrupt ledgers block startup. Synchronous flush/replace failures reach the native submission guard. Normal AutoRetainer configuration and pinned ECommons are unchanged.

NPC/retainer vendor sales, managed desynthesis and armoire storage now use a shared write-before-submit guard with fresh policy/identity checks after persistence. They wait for exact source and total reductions before clearing the journal; armoire also requires loaded cabinet ownership. Subsequent workflow steps wait while acknowledgement is pending. Dialog automation stays paused while the transaction is pending. Reviewed GC/slot state resets only after the ledger write succeeds. Clear/detach reject active jobs, dialogs and pending work. Withdrawal IPC binds retainer ID and HQ in addition to the original source fields. Native acceptance and safe cross-zone collection refresh remain outstanding.

Upstream reference: cc020df0efee3ea65a45117e2b89999108c702e8. Its pinned ECommons source requires a narrow ExcelPage alias with current API 15 references. The alias is injected by Directory.Build.targets, leaving the submodule pin untouched. Upstream CONTRIBUTING.md prohibits AI-generated contributions; no upstream contribution is proposed.

Native validation remains pending: all automation should first be checked with disposable test items and the companion's default dry run. Build and contract checks cannot validate game-memory readiness, UI event delivery or server acknowledgements.

## Protocol 6 storage addition

`Run(character, "Overflow")` reuses AutoRetainer's bell, retainer selection, inventory menu and optional postprocess workflow. It does not change entrust plans or disposal configuration. Retainers are visited only while `Steward.InventoryPolicy.OverflowNeeded(character)` is true. The companion submits exact single equipment slots through `Store(character, JSON)`, with the same container/slot/item/HQ/quantity/retainer identity as retrieval. Only an owned handoff, loaded destination pages, free space, absence of a unique-item conflict, existing upstream protection checks and an explicit `Store` permission permit the native entrust command. General unmanaged entrust behaviour is unchanged.

The existing submission journal now additionally captures the retainer destination count for `Store`. Both exact source removal and destination growth must be acknowledged before completion. `SubmissionPending()` exposes that transaction's status so Steward does not release its own operation journal early. Missing/mismatched acknowledgements, cancellation and restart retain review holds. Old bridge/companion combinations deny execution because protocol versions differ. The companion also keeps a separate durable collection hold after a successful storage transaction.
